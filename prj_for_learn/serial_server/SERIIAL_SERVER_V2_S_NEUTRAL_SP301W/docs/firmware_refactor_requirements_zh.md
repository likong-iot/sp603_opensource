# 基础分发固件需求文档（接口封装版）

- 文档版本: v1.1
- 更新日期: 2026-04-17
- 适用项目: `SERIIAL_SERVER_V2_S`
- 文档性质: 需求基线（用于后续设计与实现）

## 1. 文档目的

本文档定义“基础分发固件”的需求边界。

该固件定位不是完整业务固件，而是一个可复用、可二次开发的源码分发底座，重点提供：

1. 外设封装接口。
2. 协议封装接口。
3. 配置存储接口。
4. 最小化 Web 配置页面（仅 3 项功能）。

## 2. 产品定位

本固件定位为“平台型基础固件/SDK 样板”，用于给后续项目分发源码并快速二开。

- 提供统一接口与模块边界。
- 不承载具体业务流程。
- 不实现复杂业务编排策略。
- 重点是“可扩展性”和“可集成性”。

## 3. 核心原则

1. **只做封装，不做业务**
   - 本版不实现具体业务逻辑（如平台上报策略、设备场景规则、复杂路由策略）。
2. **接口优先**
   - 对外暴露稳定接口，内部实现可替换。
3. **模块解耦**
   - 协议层、串口层、配置层之间不得出现硬耦合。
4. **可分发二开**
   - 代码结构和 API 文档必须适合二次开发接入。

## 4. 范围定义

### 4.1 In Scope（本次要做）

1. 外设模块封装（GPIO/UART/基础定时器等）接口化。
2. 协议模块封装（MQTT/TCP/HTTP/UDP 等）接口化。
3. 配置与 NVS 统一封装接口。
4. Web 页面仅实现以下 3 项：
   - 配网
   - 配串口
   - 串口调试助手
5. API 契约整理（面向上述 3 项 Web 功能）。
6. 提供可运行的最小骨架（接口可调，流程可验证）。

### 4.2 Out of Scope（本次不做）

1. 不实现复杂业务逻辑（数据上报策略、规则引擎、业务流程控制）。
2. 不实现完整平台对接策略（如完整云端生命周期流程）。
3. 不实现全量工作模式业务闭环（只保留接口能力）。
4. 不做大规模 UI 功能扩展（系统状态页、协议管理页等均不在本次范围）。

## 5. 总体架构要求

系统至少分为以下层级：

1. `config_service`：统一配置读写与校验。
2. `serial_service`：统一串口配置、收发与事件。
3. `protocol_service`：统一协议连接、断开、收发、状态。
4. `hal_adapters`：各外设适配层。
5. `web_minimal`：最小 Web 功能（配网、配串口、串口调试）。

强制约束：

1. 协议层不得直接操作 UART 驱动细节。
2. 串口层不得直接依赖协议连接句柄。
3. 上层模块不得直接散写 NVS，必须通过 `config_service`。
4. Web 不得直接操作驱动层，只走 API。

## 6. 功能需求

### 6.1 配置服务（Config Service）

- FR-CFG-001: 提供统一初始化接口。
- FR-CFG-002: 提供 `get/set/commit` 接口（string/int/bool）。
- FR-CFG-003: 提供默认值加载能力。
- FR-CFG-004: 提供基础校验能力（范围、格式）。
- FR-CFG-005: 提供配置键集中定义，避免散落常量。

### 6.2 串口服务（Serial Service）

- FR-SER-001: 提供串口初始化接口。
- FR-SER-002: 提供串口参数配置/重配置接口。
- FR-SER-003: 提供统一发送接口（二进制/文本）。
- FR-SER-004: 提供接收回调注册接口。
- FR-SER-005: 提供串口启停接口。
- FR-SER-006: 提供状态查询接口（运行状态、错误码）。

### 6.3 协议服务（Protocol Service）

- FR-PRO-001: 提供统一生命周期接口：`start/stop/status`。
- FR-PRO-002: 提供统一发送接口：`send`。
- FR-PRO-003: 提供统一接收事件回调接口。
- FR-PRO-004: 各协议模块参数读取统一通过 `config_service`。
- FR-PRO-005: 协议模块允许“空实现/桩实现”，但接口必须完整。

### 6.4 外设封装（Peripheral/HAL Adapters）

- FR-HAL-001: 每类外设提供独立适配接口头文件。
- FR-HAL-002: 对外暴露统一错误码与返回语义。
- FR-HAL-003: 上层不得直接包含芯片私有驱动头（通过服务层间接调用）。

### 6.5 Web 最小功能（仅三项）

- FR-WEB-001: 配网页面
  - 支持 DHCP/静态 IP
  - 支持 WiFi 基础配置（SSID/密码）
- FR-WEB-002: 配串口页面
  - 波特率、数据位、校验位、停止位、帧参数
- FR-WEB-003: 串口调试助手
  - 支持 HEX/ASCII 发送
  - 支持实时接收显示
  - 支持基础收发日志展示

## 7. 接口与契约要求

### 7.1 API 要求

1. 统一响应结构：`code`, `msg`, `data`。
2. 统一错误码分层：参数错误、状态错误、内部错误。
3. 最小 API 集覆盖以下能力：
   - 网络配置读写
   - 串口配置读写
   - 串口数据发送
   - 串口实时接收（WebSocket）

### 7.2 WebSocket 要求

1. 用于串口调试助手实时收发展示。
2. 消息字段至少包含：方向（TX/RX）、时间戳、负载数据。
3. 支持大包分片标识（可选但建议保留）。

## 8. 非功能需求

- NFR-001 稳定性: 接口层运行稳定，不因空实现导致崩溃。
- NFR-002 可维护性: 新协议/新外设可按模板快速接入。
- NFR-003 可读性: 模块边界清晰，目录结构适合对外分发。
- NFR-004 可扩展性: 允许后续在不破坏接口的前提下补业务逻辑。
- NFR-005 资源约束: 基础固件应保持轻量，不引入不必要常驻任务。

## 9. 实现策略要求

1. 本版采用“骨架优先”策略：
   - 先接口定义
   - 再最小实现
   - 最后联通 Web 三项功能
2. 允许协议模块使用桩实现（stub），但需具备：
   - 可初始化
   - 可返回状态
   - 可记录调用
3. 严禁把旧业务逻辑直接搬进新接口层。

## 10. 验收标准

1. 外设与协议均已形成可调用接口（头文件 + 源文件）。
2. 任一上层模块不再直接散写 NVS。
3. Web 仅包含并可用以下三项：
   - 配网
   - 配串口
   - 串口调试助手
4. 串口调试助手可完成基础发包与回包显示。
5. 工程可编译、可烧录、可启动，核心接口路径可验证。
6. 文档中明确标记“未实现业务逻辑”的模块清单。

## 11. 交付物

1. 本需求文档（v1.1）。
2. 接口定义文档（Config/Serial/Protocol/HAL）。
3. 最小 API 文档（仅 Web 三项功能）。
4. 模块桩实现清单。
5. 基础联调说明（如何验证三项 Web 功能）。

## 12. 里程碑建议

1. M1: 接口分层与目录结构完成。
2. M2: Config/Serial/Protocol/HAL 接口完成并可编译。
3. M3: Web 三项功能页面与 API 联通。
4. M4: 最小联调验收与源码分发打包。

## 13. 风险与对策

- R1: 接口定义过粗，后续二开频繁改动。
  - 对策: 先固化最小核心接口，再扩展可选接口。
- R2: 旧代码迁移时夹带业务逻辑。
  - 对策: 评审时强制检查“接口层不得含业务策略”。
- R3: Web 需求膨胀。
  - 对策: 严格限制为三项功能，超出项进入后续版本。

## 14. 版本说明

- v1.1: 调整为“基础分发固件”定位，仅保留接口封装与最小 Web 功能。
